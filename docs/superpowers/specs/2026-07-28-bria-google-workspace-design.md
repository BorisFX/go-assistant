# Брия: Google Workspace как рабочее пространство проектов

Дата: 2026-07-28
Инстанс: Брия (юридическое и техническое сопровождение объектов недвижимости)

## Цель

Дать Брии рабочее пространство в Google Workspace: Drive хранит документы
проектов, Sheets ведёт реестр статусов, Gmail поставляет входящую переписку и
отправляет исходящую. Поверх этого — сводный отчёт по всем проектам, который
кладётся файлом в Drive.

Проект в терминах Брии — сопровождение одного объекта через полный жизненный
цикл: аренда земли → исходно-разрешительная документация → проектирование →
разрешение на строительство → строительство → ввод в эксплуатацию →
регистрация права собственности.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Форма Брии | уже работающий инстанс общего бинарника, свой `config.yaml`, БД и Telegram-бот |
| Хранилище | Drive основной; Mail.ru Cloud остаётся для чтения старого архива |
| Источник правды по статусам | Google Sheets — единый реестр проектов |
| Источник правды по документам | Google Drive — папка на проект |
| Роль Postgres | только идемпотентность разбора почты; зеркала проектов нет |
| Доступ к Google | service account + domain-wide delegation (Workspace) |
| Отчёт | по запросу, результат — файл в Drive, в Telegram ссылка |
| Масштаб | десятки проектов |

### Почему в Postgres нет таблицы проектов

Изначально рассматривался гибрид «Drive — правда, Postgres — производный
индекс для быстрых отчётов». После выбора Sheets в качестве носителя статусов
этот индекс перестал себя окупать: весь реестр читается одним вызовом Sheets
API, поэтому отчёт и так строится за один проход. Зеркало добавило бы
синхронизацию, разрешение рассинхрона и класс багов «в БД одно, в таблице
другое» ради экономии одного HTTP-запроса.

Postgres остаётся ровно для того, чего Sheets дать не может: гарантии, что
одно письмо не будет разобрано дважды.

## Внешние предусловия

До начала реализации администратор Google Workspace должен:

1. создать service account и выдать JSON-ключ;
2. включить Drive API, Sheets API, Gmail API в проекте Google Cloud;
3. добавить service account участником Shared Drive «Брия» с правом
   редактирования — для Drive и Sheets impersonation не требуется;
4. настроить domain-wide delegation для service account со scope
   `https://www.googleapis.com/auth/gmail.modify` и
   `https://www.googleapis.com/auth/gmail.send`.

Пункт 4 обязателен: Gmail API не работает с сервисным аккаунтом без
делегирования — обращения идут от имени пользователя, указанного в
`google.impersonate`. Это единственный внешний блокер всей работы.

## Декомпозиция

Четыре этапа. Каждый получает собственный план реализации и даёт проверяемый
результат. Порядок жёсткий: этап 1 — фундамент для всех; этап 3 невозможен без
реестра из этапа 2; этап 4 требует готового реестра, чтобы маршрутизировать
вложения.

**Этап 1 — Google-фундамент.** Авторизация service account, driven-адаптеры
Drive и Sheets, инструмент `drive_files`. Результат: бот читает и пишет в
Shared Drive; `legalreview` умеет разбирать папку из Drive, а не только из
Mail.ru.

**Этап 2 — Реестр проектов.** Шаблон папок, реестр в Sheets, инструмент
`projects` с действиями `list`/`get`/`create`/`set_stage`. Результат:
«создай проект Ленина 42» разворачивает скелет папок и строку в реестре;
«какие проекты на стадии РНС» отвечает из реестра.

**Этап 3 — Сводный отчёт.** Сборка отчёта из реестра, рендер в `.md`, загрузка
в Drive, ссылка в Telegram.

**Этап 4 — Gmail.** Адаптер и инструмент `gmail` (`search`/`read`/`send`),
затем фоновый разбор входящих по cron с маршрутизацией вложений в проекты.

## Архитектура

Гексагональная, как весь репозиторий. Зависимости app-слоя описываются узкими
интерфейсами, объявленными локально в пакете-потребителе, с compile-time
проверками, что реальные типы им соответствуют — приём из
`internal/app/legalreview/orchestrator.go:14-22`, позволяющий тестировать
пакет фейками без обращения к Google API.

```
internal/domain/entity/project.go        — Project: slug, адрес, этап, срок,
                                            ответственный, ID папки

internal/adapter/driven/google/
  auth.go      — SA JSON → oauth2.TokenSource; impersonation для Gmail
  drive.go     — list, search, get, download, upload, mkdir, ensurePath
  sheets.go    — чтение реестра, append строки, обновление ячеек
  gmail.go     — search, get, attachments, send, label

internal/app/projects/
  registry.go  — строка Sheets → Project, валидация, поиск по имени и адресу
  scaffold.go  — создание проекта: скелет папок и строка в реестре
  report.go    — сборка сводного отчёта
  ingest.go    — письмо → проект → вложения (этап 4)

internal/adapter/driven/postgres/project_email_repo.go

internal/tooling/builtin/
  drive_files.go, projects.go, gmail.go

migrations/005_project_emails.sql
```

Регистрация инструментов — в `cmd/assistant/main.go` рядом с существующими,
по тому же принципу гейта на конфиге: пустое значение отключает функцию, и
конфиги других инстансов не требуют изменений.

## Конфигурация

Новая секция в `config.yaml` Брии. Пустой `credentials_file` означает, что ни
один Google-инструмент не регистрируется. `gmail.enabled: false` оставляет
Drive и Sheets, но отключает почту.

```yaml
google:
  credentials_file: ${GOOGLE_SA_JSON}
  impersonate: "bria@company.com"       # subject для DWD; нужен только Gmail
  drive:
    root_folder_id: "0AB..."            # Shared Drive «Брия»
  sheets:
    registry_id: "1AbC..."
    registry_sheet: "Проекты"
  gmail:
    enabled: true
    ingest_query: "in:inbox -label:Брия/Обработано"
    processed_label: "Брия/Обработано"
    poll_interval: 15m
```

Валидация при старте: если `credentials_file` задан, файл должен существовать
и разбираться как ключ service account, а `drive.root_folder_id` и
`sheets.registry_id` не должны быть пустыми. Если включён `gmail`, обязателен
`impersonate`. Проверки жёсткие, с падением на старте — как сделано для
`legal_review` в `pkg/config/config.go:185-198`.

## Модель данных

### Реестр в Sheets

Лист `Проекты`, первая строка — заголовки, каждая следующая — проект.

| Колонка | Назначение |
|---|---|
| A `Проект` | slug, он же имя папки: `Ленина_42` |
| B `Адрес` | человекочитаемый адрес объекта |
| C `Этап` | одно из значений перечня ниже |
| D `Срок` | ближайший контрольный срок, дата |
| E `Ответственный` | имя сотрудника |
| F `Папка` | `=HYPERLINK` на папку проекта в Drive |
| G `Контакты` | адреса, с которых приходит почта по проекту |
| H `Заметка` | свободный текст |

Перечень этапов: `Земля`, `ИРД`, `Проект`, `Разрешение`, `Строительство`,
`Ввод`, `Регистрация`, `Завершён`. Значение вне перечня не роняет разбор —
проект попадает в отчёт в раздел «нераспознанный этап», чтобы опечатка в
таблице не прятала проект от глаз.

Пустая строка считается концом данных. Строка без заполненной колонки A
пропускается.

### Шаблон папок

```
Брия (Shared Drive)
├── Отчёты/
├── _Разобрать/                    вложения писем без определённого проекта
└── Ленина_42/
    ├── 10_Земля/                  договор аренды, кадастр, межевание
    ├── 20_ИРД/                    ГПЗУ, технические условия, СПОЗУ
    ├── 30_Проект/                 проектная и рабочая документация, экспертиза
    ├── 40_Разрешение/             разрешение на строительство
    ├── 50_Строительство/          акты, журналы, предписания
    ├── 60_Ввод/                   ЗОС, разрешение на ввод
    ├── 70_Регистрация/            ЕГРН
    └── 90_Переписка/              вложения из почты
```

Шаблон — константа в `scaffold.go`; добавление раздела не требует миграции
существующих проектов, поскольку папки создаются по требованию.

### Таблица в Postgres

`migrations/005_project_emails.sql`, по конвенции репозитория: только вперёд,
без отката, идемпотентный DDL, UUID генерируется в Go.

```sql
CREATE TABLE IF NOT EXISTS project_emails (
  id                UUID PRIMARY KEY,
  gmail_message_id  TEXT NOT NULL UNIQUE,
  thread_id         TEXT,
  project_slug      TEXT,
  subject           TEXT,
  from_addr         TEXT,
  received_at       TIMESTAMPTZ,
  attachments_saved INT  NOT NULL DEFAULT 0,
  classified_by     TEXT NOT NULL,
  processed_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_project_emails_slug ON project_emails(project_slug, received_at DESC);
```

`project_slug` допускает NULL — это письмо, для которого проект определить не
удалось. `classified_by` принимает `rule`, `llm` или `manual`.

## Инструменты

Все три — с диспетчеризацией по действию через `enum` в схеме, как у
существующего `cloud_files` (`internal/tooling/builtin/mailru.go:70-89`).
Единообразие контракта помогает и модели, и правилам классификатора
(`internal/app/chat/classifier.go:24-29`), которые по словам «диск», «почта»,
«проект» подгружают схемы только нужных инструментов.

| Инструмент | Действия |
|---|---|
| `drive_files` | `list`, `search`, `read`, `download`, `upload`, `mkdir` |
| `projects` | `list`, `get`, `create`, `set_stage`, `report` |
| `gmail` | `search`, `read`, `send` |

Действие `projects.report` появляется на этапе 3, остальные — на этапе 2.

Ошибки инструментов возвращаются внутри результата, а не как Go error — как
это делает `internal/tooling/executor.go:34-64`, чтобы модель могла объяснить
пользователю, что именно не получилось.

## Потоки

### Создание проекта

`projects.create` с адресом объекта:

1. нормализовать имя в slug (`Ленина 42` → `Ленина_42`);
2. проверить, нет ли такого проекта в реестре;
3. создать папку проекта в корне Shared Drive и подпапки шаблона;
4. дописать строку в реестр со ссылкой на папку и этапом `Земля`;
5. вернуть ссылку на папку.

Атомарности между Drive и Sheets нет, поэтому семантика — **ensure, а не
create**: шаг 3 находит уже существующую папку по имени вместо создания
дубликата, шаг 4 не добавляет вторую строку для существующего slug. Если
Sheets откажет после шага 3, инструмент вернёт ошибку с ID созданной папки, а
повторный вызов доведёт создание до конца.

### Сводный отчёт

`projects.report`:

1. одним вызовом прочитать весь реестр;
2. кодом посчитать срезы: распределение по этапам; просроченные (срок раньше
   сегодняшнего дня); горящие (срок в пределах 14 дней); без срока. Срез
   «без движения по почте больше 30 дней» считается по `project_emails` и
   поэтому добавляется на этапе 4, вместе с разбором входящих;
3. дешёвой моделью написать резюме «что требует внимания» — **только связный
   текст; все числа, списки и даты подставляет код**, иначе отчёт начнёт
   расходиться с реальностью;
4. отрендерить `.md` и загрузить в `Брия/Отчёты/Сводка_ГГГГ-ММ-ДД.md`;
5. вернуть в Telegram короткую выжимку и ссылку на документ.

Комплектность документов по разделам папки в отчёт не входит: это отдельный
вызов Drive на каждый проект, а ценность появится только после того, как
шаблон папок обкатается на реальных делах.

### Разбор входящих

Периодическая задача с интервалом `gmail.poll_interval`:

1. выбрать письма по `ingest_query`;
2. отсеять те, чей `gmail_message_id` уже есть в `project_emails`;
3. определить проект правилами: slug или адрес проекта встречается в теме или
   теле; отправитель числится в колонке «Контакты»;
4. если правила не сработали — фолбэк на модель через `subagent.Runner` со
   списком проектов в задаче;
5. проект определён — сохранить вложения в
   `<Проект>/90_Переписка/ГГГГ-ММ-ДД_тема/`; не определён — в `_Разобрать/`,
   запись с `project_slug = NULL` и отдельное уведомление в Telegram;
6. проставить ярлык `Брия/Обработано`, записать строку в `project_emails`;
7. отправить дайджест разбора в Telegram.

Двухуровневая защита от повторов: уникальность `gmail_message_id` в БД и ярлык
в Gmail. Если после сохранения вложений процесс упадёт до простановки ярлыка,
запись в БД всё равно не даст разобрать письмо второй раз.

Отказ на одном письме не прерывает проход: письмо помечается неуспешным,
цикл продолжается, в конце сообщается число ошибок — та же политика частичного
отказа, что в `internal/app/legalreview/orchestrator.go:91-103`.

## Ошибки и лимиты

Повторы с экспоненциальной задержкой и джиттером на ответы 429 и 5xx от Google
API, поверх существующего circuit breaker из `internal/observability`.
Обновление токена берёт на себя `oauth2`, отдельного цикла не требуется.
Списки файлов и сообщений запрашиваются постранично, размер страницы
ограничивается, чтобы длинная папка не выедала квоту за один проход.

## Тестирование

Google-адаптеры тестируются против `httptest` с записанными ответами API —
живых обращений в тестах нет. Пакет `projects` тестируется фейками локальных
интерфейсов, как `legalreview`. Классификация писем покрывается таблицей
случаев: совпадение по slug, по адресу, по отправителю, конфликт двух
проектов, отсутствие совпадений. Каждый файл сопровождается парным
`_test.go` — конвенция репозитория.

## Вне объёма

Сознательно не делаем, чтобы не раздувать первую версию:

- зеркало проектов в Postgres — обосновано выше;
- проверка комплектности документов по этапам;
- индексация содержимого файлов Drive для поиска — `legalreview` уже умеет
  разбирать папку по требованию;
- вкладка «Проекты» в веб-дашборде — реестр и так открывается в Sheets;
- миграция архива из Mail.ru Cloud в Drive;
- поддержка нескольких Google-аккаунтов сотрудников: работаем от одного
  служебного ящика.
